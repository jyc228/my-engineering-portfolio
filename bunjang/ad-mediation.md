# 광고 미디에이션 전환 (AdMob → DARO): 직군 간 경계 다시 자르기

## 프로젝트 개요

- 기간: 2026.04 (약 1개월), 이후 2026.09 번개복권 광고 형식 라우팅 확장
- 참여: 네이티브 2명 (iOS, Android 각 1명), 프론트엔드 3명, 백엔드 3명 (3개 팀에서 한 명씩), 기획 1명
- 주요 역할: 백엔드 리드, 직군 간 연동 구조 설계
    - 백엔드 구조 결정, 3개 팀 백엔드 API 스펙 정리
    - 네이티브·프론트엔드·백엔드 사이의 연동 구조 제안 (채택)
    - 번개복권, 광고 보고 UP하기 백엔드 구현

## 한줄 요약

광고 SDK 를 교체할 때마다 네이티브, 프론트엔드, 백엔드가 전부 불려 나오던 구조를,
SDK 의존성은 서버와 네이티브에만 두고 웹뷰는 데이터를 해석하지 않고 넘기기만 하도록 경계를 다시 잘랐습니다.

## 배경

광고를 보고 보상을 받는 서비스가 세 개(번개복권, 설렘박스, 꽃피우기) 있습니다.
규모가 크지 않아 파트별로 따로 담당하고 있었고, 각각 독립 프로젝트라 백엔드 API 규격도 서로 달랐습니다.

광고 자체는 세 서비스 모두 같은 방식으로 띄웁니다.
웹뷰가 JSI(JavaScript Interface)로 앱을 호출하면, 앱이 광고 SDK 로 광고를 불러와 웹뷰 위에 표시합니다.

이번 작업은 광고 SDK 를 AdMob 에서 미디에이션 솔루션 DARO 로 바꾸는 것이었습니다.

## 문제

대화를 정리해 보니 SDK 교체가 어려운 이유는 SDK 자체보다 구조에 있었습니다.

- **JSI 가 AdMob 전용이었습니다.** 광고 "타입" 이 보상형/전면형이 아니라 SDK 종류(AdMob)를 뜻했고, 서비스마다 JSI 를 호출하는 방식도 달랐습니다.
- **SDK 선택이 웹뷰까지 퍼져 있었습니다.** 어떤 서비스는 서버가 내려준 타입으로 프론트엔드가 JSI 를 골랐고, 어떤 서비스는 프론트엔드가 앱 버전을 읽어 직접 분기했습니다.
- **설정 주도권이 흩어져 있었습니다.** 광고 보고 UP하기는 광고 유닛 ID 가 네이티브에 하드코딩되어 있어서, 관련 변경이 백엔드까지 전달되지 않았습니다. 이 서비스의 백엔드는 제가 처음 만들었는데, 그때 이 부분을 챙기지 못했습니다.

그래서 광고와 관련된 변경이 생길 때마다 모든 직군이 회의에 불려 나왔습니다.
처음 논의에서도 "DARO 전용 JSI 를 새로 만들고 버전 체크 JSI 를 추가하자" 같은, 다음 교체 때 같은 일을 반복하게 되는 방향이 나오고 있었습니다.

## 제안: SDK 의존성은 서버와 네이티브에만

미디에이션사에 대한 의존성은 원래 두 곳에만 있으면 됩니다.

- 서버: 어떤 광고 유닛 ID 를 쓸지
- 네이티브: 어떤 SDK 로 광고를 불러올지

이 의존성을 웹뷰까지 퍼뜨리면, 앞으로 비슷한 작업마다 프론트엔드도 같이 움직여야 합니다.
그래서 다음 구조를 제안했고 채택되었습니다.

1. 서버의 광고 유닛 API 응답에 **미디에이션사를 식별하는 필드**를 추가합니다.
2. 웹뷰는 이 데이터를 해석하지 않고 **JSI 로 네이티브에 그대로 넘깁니다.**
3. 네이티브는 넘겨받은 값으로 **어떤 SDK 로 광고를 불러올지 결정**합니다.

당시 네이티브는 SDK 를 하나만 쓸 수 있는 상태라 이 식별 필드가 당장은 의미가 없었습니다.
하지만 앞으로도 그러리라는 보장이 없어서 필드를 두기로 했고, 실제로 이후 기획 쪽에서 DARO 가 채우지 못한 지면을 다른 SDK 로 백필하는 시나리오가 나왔습니다.

## 직군별로 정한 원칙

| 직군 | 원칙 |
|---|---|
| 네이티브 | 광고 SDK 동작은 JSI 파라미터로만 제어한다. 파라미터에 없는 값을 내부에서 암묵적으로 판단하지 않는다. |
| 프론트엔드 | 광고 관련 데이터는 해석하지 않고 서버 응답을 JSI 로 그대로 넘긴다. |
| 백엔드 | 세 프로젝트를 합칠 수는 없으니 API 스펙만 통일한다. 광고 형식(`REWARD`, `INTERSTITIAL`), 미디에이션사(`DARO`, `ADMOB`), 광고 유닛 ID. |

새 JSI 스펙에서 광고 형식이 처음엔 `video` / `interstitial` 로 되어 있었는데, 이러면 프론트엔드가 백엔드 값(`REWARD`)을 JSI 값(`video`)으로 바꾸는 매핑을 해야 합니다.
"클라이언트는 최대한 데이터를 보지 않고 처리한다" 는 원칙에 맞춰, 아직 수정 가능한 시점에 JSI 값을 백엔드 enum 과 같게 맞췄습니다.

구버전 앱은 프론트엔드가 앱 버전으로 한 번만 분기합니다. 새 버전 이상은 서버 값을 그대로 넘기고, 그 아래 버전만 기존 AdMob JSI 를 호출합니다.

## 광고 유닛 ID 는 서버가 관리하고, 조회 API 는 하나의 스펙으로

광고 보고 UP하기는 이번에 광고 유닛 ID 를 네이티브 하드코딩에서 서버 관리로 옮겼습니다.
SDK 가 바뀔 때마다 앱을 배포하지 않아도 되고, 비즈니스 목적으로 지면마다 다른 ID 를 부여할 수도 있기 때문입니다.

그런데 네이티브가 프리로드를 하려면 광고를 보기 전에 광고 유닛 ID 를 먼저 알아야 했습니다.
번개복권과 광고 보고 UP하기는 보상을 요청하는 POST API 에서만 ID 를 내려주고 있었고,
프리로드와 시청 시점에 최소 두 번 호출하게 되면 POST 로는 불필요한 쓰기가 생깁니다. 그래서 조회용 GET API 를 따로 만들기로 했습니다.

다른 서비스도 같은 상황일 것 같아 스레드를 열어 확인해 보니, 꽃피우기에는 이미 필요한 필드를 모두 내려주는 GET API 가 있었습니다.
새 스펙을 만드는 대신 **이미 있는 API 에 나머지 세 서비스를 맞췄습니다.** 꽃피우기는 수정할 것이 없어졌고, 나머지는 필드 이름까지 같은 응답을 내려줍니다.

```json
{
  "data": {
    "adNetwork": "daro",          // admob, daro
    "adUnitId": "...",
    "adUnitType": "INTERSTITIAL", // REWARD, INTERSTITIAL
    "preload": true
  }
}
```

보상을 요청하는 POST API 응답에도 같은 필드를 함께 넣었습니다. 조회 API 를 먼저 호출해야만 보상 API 를 쓸 수 있는 식의 API 간 의존을 만들지 않기 위해서입니다.
기존 응답의 `network` 필드는 이제 의미가 없지만, 하위 호환을 위해 남겨 두었습니다.

## 프리로드: 지금 결정하지 않고 서버가 정하게

논의 중간에, 프리로드를 너무 많이 하면 낙찰된 광고가 시청되지 않아 매체 가치(eCPM)가 떨어질 수 있다는 의견이 나왔습니다.
반대로 프리로드를 빼면 광고 로딩이 길다는 VoC 가 다시 늘 수 있었습니다. 둘 다 DARO 를 실제로 붙여 보기 전에는 알 수 없는 값이었습니다.

그래서 지금 결정하지 않고, 광고 유닛 조회 API 에 미디에이션사별 프리로드 여부 필드를 추가해 서버에서 제어하도록 했습니다.
웹뷰를 거치는 서비스는 프론트엔드가 이 값을 JSI 로 넘기고, 네이티브가 직접 호출하는 화면은 같은 API 로 판단합니다.
이렇게 하면 운영하면서 eCPM 과 VoC 를 보고 앱 배포 없이 조정할 수 있습니다.

## 보상 서버 검증 연동

보상형 광고는 시청이 끝나면 광고 네트워크가 우리 서버로 보상 검증 콜백(SSV)을 보내고, 서버가 이를 확인한 뒤 보상을 지급합니다.
광고 보고 UP하기에 DARO 의 SSV 콜백을 연동했습니다.

DARO 는 AdMob 과 사용자 식별 데이터를 넘기는 방식이 달라서, 앱과 함께 테스트하는 동안 콜백이 오지 않거나 엉뚱한 값이 오는 일이 있었습니다.
Datadog 에서 실제로 들어온 콜백을 확인해, 앱이 보상 식별자 대신 사용자 ID 를 `custom_data` 에 넣고 있던 것을 찾아 바로잡았습니다.

## 결과

- 번개복권, 광고 보고 UP하기 백엔드를 직접 작업해 운영 배포 (DARO 보상 서버 검증 연동 포함)
- 네 지면의 광고 조회 API 를 기존 꽃피우기 API 스펙으로 통일, 미디에이션사별 프리로드 서버 제어
- 광고 보고 UP하기의 광고 유닛 ID 를 네이티브 하드코딩에서 서버 관리로 이전
- 운영 중 프리로드 설정을 서버 값 변경만으로 조정 (앱 배포 없음)

## 이후: 나눈 경계가 실제로 한 일

- **번개복권에 확률적 광고 형식 라우팅을 서버 변경만으로 추가.** 회차가 올라갈수록 보상형과 전면형 광고가 확률적으로 섞여 나오도록 바꿨습니다. 광고 형식을 서버가 정해 내려주고 클라이언트는 그대로 넘기는 구조라, 프론트엔드와 네이티브는 아무것도 바꾸지 않았습니다.
- **SDK 에러 코드 노출 작업이 백엔드까지 오지 않음.** 이후 광고 SDK 의 에러 코드를 사용자에게 보여주는 작업이 진행되었습니다. JSI 콜백에 에러 코드 파라미터가 추가되고 네이티브와 프론트엔드가 함께 수정했지만, 논의와 변경은 모두 JSI 를 사이에 둔 두 직군 안에서 끝났고 백엔드는 아무것도 바꾸지 않았습니다.
- **SDK 메이저 업데이트(DARO 2.0)에도 백엔드 작업 없음.** SDK 2.0 에서 광고 유닛 ID 가 새 키로 바뀐다는 안내가 있어 백엔드 대응이 필요할 수 있다는 의견이 나왔습니다.
  문서와 DARO 답변을 확인해 보니 기존 ID 를 그대로 써도 되고 새 키로의 갱신은 권장 사항이었습니다.
  광고 유닛 ID 를 이미 서버가 관리하고 있어서, 송출이 나빠지는 게 계측되면 그때 서버 값만 바꾸면 됩니다. 그래서 이번에는 대응하지 않기로 했습니다.

이 작업에서 제가 가장 원했던 건, 광고 관련 작업을 할 때마다 모든 직군이 불려 나오지 않는 것이었습니다.
각 직군이 자기 영역의 지식만으로 변경을 처리할 수 있도록 경계를 정하는 것이 이번 작업의 핵심이었습니다.
